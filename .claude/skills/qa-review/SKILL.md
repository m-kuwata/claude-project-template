# QA レビュースキル — 実運用整合チェック

> **目的**: テストが「コードの動作確認」ではなく「現場で起きること」を検証しているかを見る。
> ユニットテストの合否ではなく、シナリオ設計の妥当性をレビューする。
>
> **このファイルの調整方法**: ステップ 2 の A〜B のチェック項目は、
> プロジェクトのドメイン（対象ユーザー・実データ規模・現場で起きる事故）に合わせて
> 具体化すること。C〜F は汎用なのでそのまま使える。
> ドメインの依り所は `docs/product-context.md` 等を参照する。

---

## ステップ 1 — コンテキスト収集

```bash
# レビュー対象のテストファイルを確認
git diff --name-only HEAD | grep -E '\.(test|spec)\.(ts|tsx|py)$'

# 対応する issue を特定
git log --oneline -10   # コミットメッセージから issue 番号を抽出
```

対応 issue を GitHub で確認し、以下を把握する:
- **ユーザーストーリー**: 誰が・何をしたいか
- **受け入れ条件**: 何が満たされれば完了か
- **背景**: なぜこの機能が必要か

---

## ステップ 2 — 実運用整合チェックリスト

### A. シナリオが「現場の動き」を表しているか（★ドメインに合わせて具体化）

- [ ] テストデータが**実際の運用規模**を反映している（極小すぎる入力になっていないか）
- [ ] 典型的なユーザーの**主要ワークフロー**を再現したシナリオがある
- [ ] 「正常」「不足」「過多」など現場で起きる状態のバリエーションがある

> 例（学校時間割アプリの場合）: クラス数 3〜6、教科数 9〜12、週 30 スロットなど、
> 実際の規模を反映する。プロジェクトのドメインに置き換えること。

### B. エッジケースが「机上のケース」ではなく「現場で起きる事故」か（★ドメインに合わせて具体化）

- [ ] 実運用で**実際に起きうる失敗・競合**を再現している（理論上のみのケースではなく）
- [ ] 境界値（上限ちょうど・ゼロ件入力）のテストがある
- [ ] 過去に起きた本番事故のパターンをカバーしている

### C. テストの「視点」が正しいか

- [ ] **ユーザーが見る結果**を assert している（内部カウンタや中間状態ではなく）
  - ✅ 出力データそのものを検証 — ユーザー視点
  - ❌ 内部変数の直接確認
- [ ] **失敗したときのメッセージ**が「何が壊れたか」を人間に伝えられる形になっている
- [ ] テスト名が**日本語・ユーザー視点**で書かれている
  - ✅ `it("同一担当者は同時刻に2つの予定を持てない")`
  - ❌ `it("should not allow conflict")`

### D. 「ハッピーパス偏重」になっていないか

| 種別 | 理想比率 |
|---|---|
| 正常系（期待通り動く） | 40% |
| 境界値・制約ぎりぎり | 30% |
| 異常系・制約違反で弾かれる | 20% |
| 回帰（過去バグの再現） | 10% |

- [ ] 異常系（エラー返却・空結果・失敗）のテストが 1 件以上ある
- [ ] 境界値のテストがある

### E. 回帰テストが「バグの再現」になっているか

- [ ] バグ修正に対応するテストは、バグが起きた入力条件を再現しているか
- [ ] バグ番号（`#303` など）がテスト名またはコメントに含まれているか

### F. BDD 命名規約 — issue 受け入れ条件との対応

- [ ] テスト名が「〈ユーザー〉が〈操作〉すると〈結果〉になる」形式になっているか
- [ ] 対応する issue の受け入れ条件と **文字列レベルで対応している**か
- [ ] `describe` が機能名 or issue タイトルを表しているか（実装クラス名・ファイル名になっていないか）
- [ ] 受け入れ条件が「ユーザー不在・実装語」になっていた場合は、issue 本文の修正も提案する

---

## ステップ 3 — 不足シナリオの洗い出し

チェックリストで ✗ が付いた項目について、不足しているテストシナリオを列挙する。

---

## ステップ 4 — 改善提案のフォーマット

不足シナリオは以下のフォーマットで issue or コメントに記録する:

```
【QAレビュー: <テストファイル名>】

✅ カバーできているシナリオ
- ...

⚠️ 実運用で起きうるが未カバーのシナリオ
1. <シナリオ名>: <なぜ現場で起きるか>
   → 追加すべきテスト: it("<日本語テスト名>")

🔴 特に重要（本番事故につながりうる）
- ...
```

## ステップ 5 — 完了マーカー記録（必須）

全ステップ通過後、Stop フック（`auto-qa-review.sh`）のブロックを解除するためにマーカーを置く。

```bash
bash $CLAUDE_PROJECT_DIR/.claude/hooks/mark-review-passed.sh qa-review
```

`touch /tmp/${PROJECT_NAME}-qa-review-passed` は deny リストで禁止されています。
このスクリプトを経由することで、Stop フックがスキルを正規に実行したことを検証できます。
