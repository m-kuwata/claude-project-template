# PO レビュースキル — 運用整合チェック

> **目的**: 機能・issue・実装が「ターゲットユーザー」の現場課題を
> 正しく解決しているかを Product Owner 視点で検査する。
>
> **このファイルの調整方法**: スコープ判定表（Mode: create §2）と確定方針
> （Mode: start §2）は、プロジェクトの `docs/product-context.md` / CLAUDE.md の
> 「確定方針」「MVP 機能セット」に合わせて差し替えること。チェックの枠組み自体は汎用。

---

## このスキルの使い方

| タイミング | コマンド | 確認すること |
|---|---|---|
| issue 作成後 | `/po-review` (mode: create) | その issue を作るべきか |
| 実装着手前 | `/po-review` (mode: start) | 実装方針が issue の意図と合っているか |
| 実装完了後 | `/po-review` (mode: done) | 完成物が元の課題を解決しているか |

**完了後に必ず実行**:
```bash
bash $CLAUDE_PROJECT_DIR/.claude/hooks/mark-review-passed.sh po-review
```
`touch /tmp/${PROJECT_NAME}-po-review-passed` は deny リストで禁止されています。
このスクリプトを経由することで、Stop フックがスキルを正規に実行したことを検証できます。

## Mode: create — issue 作成レビュー

### 1. 課題の妥当性

- [ ] **誰の・どんな問題を解決するか**が一文で言える
  - ✅「〈ターゲットユーザー〉が、〈具体的な手間〉を減らしたい」
  - ❌「精度を上げる」（誰の何が困っているのか不明）
- [ ] ターゲットが **想定ユーザー** である（対象外のユーザー向けになっていないか）
- [ ] 個人情報を不必要に扱う機能になっていない

### 2. スコープ判定（★プロジェクトの MVP 機能セットに合わせて差し替え）

- [ ] CLAUDE.md / `docs/mvp-draft.md` のスコープ表と照合し、MVP 外の機能が含まれていないか
- [ ] 価格・コスト制約に影響する追加コスト（外部 API・有料ライブラリ）がないか

### 3. 受け入れ条件の品質

- [ ] 「ユーザーが確認できる」形で書かれているか
  - ✅「〈ユーザー〉が〈操作〉して〈結果〉を確認できる」
  - ❌「正しく保存される」（何が正しいか不明）
- [ ] 完了の判断基準が 1 つ以上ある
- [ ] 「やらないこと（Out of scope）」が明示されているか（あると望ましい）

### 4. 既存機能への影響

- [ ] 既存のデータ構造（DB スキーマ）への破壊的変更がないか
- [ ] 既存の仕様ドキュメントと矛盾しないか

---

## Mode: start — 実装着手レビュー

対応 issue の番号を `git log --oneline -5` か `/tmp/${PROJECT_NAME}-issue-acked` で確認してから実施。

### 1. 実装方針の整合

- [ ] 実装しようとしているものが、issue のタイトル・本文のゴールと一致しているか
  - 「issue に書いてあること以上」を実装していないか（スコープ超過）
  - 「issue に書いてある受け入れ条件が漏れていないか」（スコープ不足）
- [ ] より簡単な実装方法で同じ UX が実現できないか（YAGNI の観点）

### 2. 確定方針チェック（★CLAUDE.md の「確定方針」に合わせて差し替え）

CLAUDE.md の「確定方針」と照合:

- [ ] 個人情報の扱いが方針に反していないか
- [ ] 変更禁止項目（アーキテクチャ・契約モデル等）に触れていないか

### 3. 技術的整合

- [ ] ホスティング環境で動くか（環境固有の制約に反していないか）
- [ ] 影響範囲の大きいモジュールへの変更は、関連パスすべてへの影響を確認したか

---

## Mode: done — 実装完了レビュー

### 1. 課題解決の確認

- [ ] issue の「受け入れ条件」を 1 つずつ確認し、すべて満たしているか
- [ ] issue を作るきっかけになった「ユーザーの困りごと」が解消されているか
- [ ] issue に書いていない機能が追加されていないか（スコープ超過）

### 2. 副作用チェック

- [ ] 既存の機能が壊れていないか（テスト緑を確認）
- [ ] DB スキーマ変更がある場合: マイグレーションファイルが含まれているか
- [ ] CLAUDE.md・ドキュメントの更新が必要か（新しい仕様・確定方針の追加）

### 3. ユーザー体験の最終確認

「ターゲットユーザーの立場」になって確認する:

- [ ] エラーメッセージが「何をすればいいか」を教えているか
- [ ] 操作の結果が画面に反映されているか（フィードバックがあるか）
- [ ] ユーザー向け UI で専門用語を使っていないか

### 4. 完了マーカー記録

```bash
bash $CLAUDE_PROJECT_DIR/.claude/hooks/mark-review-passed.sh po-review
```
